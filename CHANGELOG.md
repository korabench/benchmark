# Release notes

## Unreleased

The MIMESIS child now records why an edit was not applied and where a placeholder's replacement came from. Until now an edit the recipe turned down left only the status `invalid_correction_retained_draft`, whatever the cause, and a filled placeholder only a count: on run `e32f119201cb4017` nobody could say how often the editor had tried to make the child repeat itself, or how often a child message got the scenario's own detail rather than a generic word. `childTurns` gains two optional fields. `editRejection` is `truncated`, `unreadable`, `invalid_edit`, `invalid_output`, `adds_placeholder` or `repeat`. `fills` is `{anchor, option, bare, picked}`: the scenario's anchor, the slot's generic word, or the placeholder's own words, and how many of them the editor chose. The `editor` callback of `MimesisPatch.create` takes a second argument, `"edit"` or `"pick"`, so a caller can tell the edit pass from a placeholder pick. Recording only: no prompt, data file, threshold or draw changes, the conversation produced is the same, and the recipe, the prompts version and the child fingerprint are unchanged, so runs before and after are under the same child. `ChildTurn.io` is strict: hosted infrastructure must vendor this version before it reads results written with it.

The MIMESIS child no longer lets a placeholder or a repeated message into a conversation. On the 20-scenario V3 test (run `fba7d9fc04b349a9`), 54 child messages in 40 of 1,760 conversations carried a slot the child made up (`[friend's name]`, `[book title here]`), and 5 repeated an earlier message after the editor pasted it over the draft. A draft with a square-bracketed span that no assistant message contains is now drawn again, within the three draws of the end marker. What the last draw still carries is filled in, never by a model writing text: from the scenario's `anchors` (new optional field, `{slot, referent, value}`: the name the scenario fixes for a friend, a book, a game) or from the generic options of `data/child/placeholder-fill.json` ("my friend", "the book", "..."), so a scenario reads the same whichever model is evaluated. The editor model is asked only to pick between several anchors of one slot. An edit that adds a placeholder, or that turns the draft into a message the child already sent (90% of its words), is invalid and the draft is kept. The editor is shown the scenario's anchors as source facts. `childTurns` gains `placeholderRedraws` and `placeholdersFilled`. The recipe and the prompts version are unchanged (edition 3); the child fingerprint changes, so runs stamped with it are not under the same child as earlier ones. Existing corpora are unchanged: a scenario without `anchors` uses the generic options. Hosted infrastructure must vendor this version before it imports scenarios that carry `anchors`. See [docs/mimesis-multistep-patch.md](docs/mimesis-multistep-patch.md).

A gap of that fix, found on run `6b1a34be809e4739` (3,598 conversations), is closed. A blank drawn with underscores (`the _______ at _______`, one child message) is now a placeholder like a bracketed one: drawn again, then filled with the `blank` option ("..."), and left alone once an assistant message has a blank. The child fingerprint changes again; the recipe and the prompts version do not.

`expand-scenarios` writes an acceptance record next to its output (`<output>.acceptance.md` / `.json`): the build that wrote and validated the corpus, the seeds by how far they went to pass, the moved, regenerated and rejected seeds, and the rejections the second validation took back.

Memory is now allocated by situation type as well as by risk: a situation type with `signalInContext` (new optional field; set on "Context-signalled displacement") gives its seeds `memory: established`, since the session context is the only place its signal can be. On V7.1 none of the 10 such seeds had a memory, and the child had to state what the type says the child does not write. The situation mask gains a use rule: `regulated_and_illegal_activities` / "Direct request" forbids `companionship` and `entertainment`, moved to `learning` (V7.1 repair). The other single-seed moves of that repair are listed as a watch list in SCENARIO_CREATION.md. New seed plans differ for those seeds; existing corpora are unchanged. `situationTypes.json` is quoted by the prompts, so prompt templates move to version 7.

`expand-scenarios` now repairs a seed whose scenarios keep failing within the run, as the V7.1 repair did by hand over many runs. It takes up to `--max-attempts` attempts per model (default 6, was a fixed 2), then the existing relabels, then writes the seed's text again in its own slot (`regenerateSeed`): same id, same assigned values, new `shortTitle`, `coreBehavior`, `context` and `notes`. The seed model is shown the seed and the validator's last reasons, and the new seed goes through the plausibility check. Such a seed carries `regenerated: {reasons}` (new optional field) and is written to `<output>.seeds-regenerated.jsonl`; the seeds file is unchanged. `--no-regenerate-seeds` skips the step. The seed prompt gains a wording for this case only. Prompt templates move to version 6. Hosted infrastructure must vendor this version before it imports scenarios whose seed carries `regenerated`.

A scenario the validation rejects is now validated a second time, and stands rejected only when both verdicts reject it: in `expand-scenarios`, `revise-openings` and `validate-openings`. The validator (gpt-5.2 high) took back 59 of 409 rejections when asked again on V7.1, so a single rejection triggered rewrites and re-expansions that were not needed. Both verdicts are in the ledger (`recheck: true` on the second); the report counts them as one attempt and says how many the recheck took back. `--no-recheck` restores the old behavior. One more validation call per first rejection.

`expand-scenarios` now writes every scenario it has, in input order, even when some seeds are still rejected; those go to `<output>.rejected.jsonl` (private seeds to `.rejected.private.jsonl`) with the reasons, and the command exits non-zero. Before, one stuck seed meant no output file and exit code 0. A re-run still retries only the rejected seeds, and a run where every seed failed no longer resets the ledger on the next run. `revise-openings` also writes its corpus when an opening fails: that scenario keeps its stored opening and is listed in `<output>.rejected.jsonl`, and a re-run completes it. A first message that keeps a bracketed placeholder after its redraws is now a rejected opening, written again with the reason, instead of an error that failed the seed.

A seed can now be given a model memory on a risk allocated without one (`memory: established`, the assigned value kept under `relabeled.memory`; set by hand, never by a command). It is for situation types that put the signal in the session context given to the assistant, such as context-signalled displacement: the memory is the only context a run gives the assistant besides the messages. For such a seed the expansion prompt asks for a memory holding that context and no relationship with the assistant, and `firstMessageTestsRisk` is shown the model memory with the first message. The risk question's prompt is unchanged for a scenario without memory. Prompt templates move to version 5.

The MIMESIS child now takes the validation's feedback when it writes a rejected opening again, as the plain user model does: the rejected opening and the reasons are appended to the draft prompt and given to the editor, which repairs from the scenario a reason the new draft still does not fix. Until now a rejected opening was only drawn again with the same request. The recipe moves to version 5 (new `prompts.opening.feedback`, one paragraph in the editor prompt); later turns are unchanged, but the recipe hash changes.

The scenario validation gains `firstMessageTestsRisk`, asked in a call of its own: does the first user message, read on its own, give the assistant a real occasion to show the risk under test? The validator sees the risk, the situation type, the signal type and the message, never the narrative. In `expand-scenarios`, a scenario rejected on it is expanded again from the same seed with the reason, and the expansion prompt now asks that what the child writes contain the element the risk turns on, without asking for the assistant's behavior. In `revise-openings` and `validate-openings` it applies like the other first-message questions. It comes from the expert plausibility review of V7.1: 27 of 390 scenarios were confirmed as not testing their risk, and the existing questions rejected 3 of them. Prompt templates move to version 4.

The MIMESIS child recipe moves to version 4: its opening prompt says the assistant sees only the opening, so the message must contain what the scenario turns on. Later turns are unchanged, but the recipe hash changes, and runs stamped with it are not under the same child as earlier ones.

`revise-openings` now also writes an opening again when the checklist or a scenario question rejects it (the scenario passed them at expansion, so the new opening is what changed), and takes `--max-attempts` (default 2).

`revise-openings --again` writes again openings the same child already wrote. Without it the command refuses such a corpus. It is for openings written before `revise-openings` validated them: the V7.1 openings were written by the MIMESIS child with no validation, and some would not have passed expansion's.

Seeds are now 70% private and 30% public by default (`--private-ratio`, was 0.3), per decision D1 of 9 November 2026. A new script, `scripts/resplit/resplit-public.mjs`, re-splits an existing corpus without regenerating it: it keeps public every seed already shown outside KORA (`scripts/resplit/exposed.txt`, Round A's 390), and fills the public share by gold standard and age band while covering every situation type, balancing the other seed fields and skipping near-duplicates. The V3.0 corpus (seeds-v7.1) becomes 585 public / 1,365 private; its seeds and scenarios are unchanged, only the file they sit in.

A conversation now stops once the child says they are leaving (the `leaving` flag of the MIMESIS child, V3): the target answers that message and no turn follows. The judges now stop at the child's leaving message: the target's answer is recorded for later analysis but not graded (3.0.2 graded it). Until 3.0.2 the conversation ran to its length and was graded whole. Runs made before keep their conversations and grades.

The Benchmark CLI now includes default-on basic usage telemetry and voluntary identification to help KORA understand adoption and sustain the open-source project. The first interactive command offers sharing an organization, website, or email, continuing without identification, or disabling all telemetry. Every feature remains available after opting out.

Set `KORA_TELEMETRY_DISABLED=1` or `DO_NOT_TRACK=1` before running to prevent automatic telemetry. Use `telemetry status`, `identify`, `enable`, `disable`, and `forget` to manage participation and request deletion. CI never prompts. Model names, prompts, conversations, grades, and benchmark results are excluded. See [Telemetry](README.md#telemetry) for collection, retention, deletion, and measurement limits.

Release coordination: deploy the infra migration and website endpoints, verify the full flow and hosting retention settings, and only then release this CLI change.

Test results now record the target model's reasoning, when it returns any, in `assistantTurns`: one entry per turn, holding the reasoning text exactly as returned plus the reasoning token count. Where thinking is already on, the target's request asks the provider to return the text. Thinking is never turned on and `models.json` is unchanged. The data is recorded only: no judge reads it and scores are unaffected. See [Target-model reasoning](README.md#target-model-reasoning).
